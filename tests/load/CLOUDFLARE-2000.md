## 结论

2000 个独立席位全部完成 300 秒共同在线窗口，零 WebSocket 错误、零意外断开。
业务压力测试未通过：28712 次 HTTP 请求，25299 次成功、3413 次 HTTP 500，成功率 88.11%，低于 90%；成功请求延迟也未达到 2 秒门槛。
这证明此短时场景的连接保持能力，不能解释为业务并发容量全面通过。

四个专用大会，每大会 500 席；180 秒接入，接入结束后开始 300 秒共同在线。
HTTP 并发上限 128，30 秒总超时（含排队），失败不自动重试。每席位每 30 秒浏览一类文件/新闻/局势列表。
每大会五个写入席位，合计 20 次文件上传，交替 64 KiB / 1 MiB，随后审批、下载 SHA-256 验证，再提交新闻或发布局势。
真实 WS 通知触发列表刷新，250ms 合并同席位同主题。不是 2000 人同时传文件，也不是长期稳定性测试。
种子仍是广权限 MPC/IPC 角色，包含审核权限；不能代表正式会议的角色比例。

## 能定位到的部分

1. 接入阶段表现正常：4000 次登录/初始加载全部成功，没有客户端队列积压。
2. 20 次文件操作集中触发真实列表刷新后，HTTP 队列采样超过 2000，排队 P95 接近 10 秒。多类业务总耗时上升到 8–12 秒，而 Worker 内 P95 多为 0.5–1 秒，说明大部分用户等待来自已测到的本机并发门控队列。128 HTTP 并发是本次发压架构的上限，并非 Cloudflare 平台上限。
3. 3413 个失败全部是 HTTP 500，且均带 Worker 分段计时，说明请求进入应用后失败，不是压测端超时或连接拒绝。文件刷新 1925、新闻浏览 956、新闻刷新 307、文件浏览 197、新闻提交 10、文件审批 8、局势发布 6、文件下载 4，合计 3413。
4. Worker 响应只给出通用错误，没有异常栈或具体 D1 错误。两次 wrangler tail 都因本机到日志服务的连接超时未能建立，无法回溯已发生的异常。因此不能确定是 D1 配额、查询异常、请求限制还是其他应用异常，不能直接写成 D1 限流。
5. R2.put P95 为 836ms，R2.get P95 为 921ms。此次云端没有重现本地 R2.put 十几秒的尾延迟；下载总耗时还包含约 10 秒排队和响应体接收（body P95 1772.53ms）。
6. Worker 密码验证计时全部为 0 是云端时钟精度限制，不表示密码验证没有 CPU 成本；没有取得 CPU profiler 数据。D1 调用耗时是等待与执行合计，不等于 SQL 纯执行耗时。
7. 集中操作后普通浏览恢复，最后采样保持 2000 席。此前本地数秒到数十秒的 ProxyWorker 外等待没有在云端接入阶段重现；两边网络和部署环境不同，不据此推断唯一根因。

四次下载 HTTP 500 在原始脚本中误标为 HASH_MISMATCH，现已纠正分类并修复脚本。原始数据保留，另存 corrected 数据；没有成功下载哈希不一致的证据。
20 次上传全部被服务端确认成功；12 次审批成功；8 次下载成功并校验一致。其余流程不完整，不能声称文件业务全部通过。
