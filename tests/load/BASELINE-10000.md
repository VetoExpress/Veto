# 10000 席本地诊断与一轮 API 修复

2026-11-11，目标为十个大会、每大会 1000 个独立席位。两次完整运行均未达到 10000 席在线，不能宣称通过万人容量验收。
环境为 Windows、32 GiB RAM、24 逻辑处理器，本地 Wrangler 4.134.0、真实 workerd/D1/R2/DO。
压测端使用 Node 24.22.1、undici 7.29.0、ws 8.21.0。没有接入 KV，没有部署或测试 Cloudflare 线上环境。

## 负载与结果

240 秒均匀发起接入，等待在途接入结束后执行 120 秒共同在线窗口。HTTP 并发上限 128，总超时 30 秒（含门控排队）。
所有认证成功席位每 30 秒浏览一种列表；每大会五个写入席位，合计 50 次文件上传，交替 64 KiB/1 MiB，之后审批和下载 SHA-256 校验，并提交新闻或发布局势。

## 有效延迟与归因

下表总耗时仅统计成功请求；其他阶段使用拿到对应样本的请求。单位 ms，P95。不同样本的分位数不能相加或相减。

| 操作与指标                                  |   修复前 |                    修复后 |
| ------------------------------------------- | -------: | ------------------------: |
| 登录成功请求总耗时                          | 28227.94 |                  27805.79 |
| 登录客户端门控排队                          | 27814.57 |                  27863.97 |
| 登录 Worker 处理                            |       45 |                        36 |
| 登录 Worker 外等待（逐请求 TTFB 减 Worker） |  9714.88 |                   7094.93 |
| 初始委员会 Worker 处理                      |       10 |                         9 |
| 文件浏览成功请求总耗时                      | 24925.61 |                  17469.80 |
| 文件浏览 Worker 处理                        |       13 |                        11 |
| 上传成功请求总耗时                          | 28635.93 |                  26131.73 |
| 上传 Worker 处理                            |    14148 |                     16767 |
| 上传 R2.put 调用                            |    13058 |                     16590 |
| 下载成功请求总耗时                          |   无样本 | 27051.15（11 个成功样本） |

1. 接入和列表延迟主要出现在明确测得的客户端排队与 Worker 外等待。基线登录密码验证 P95 为 34ms、查询邀请码 7ms、写会话 5ms。不存在“D1 单次查询花了二十多秒”的证据。
2. 本地日志出现 `ProxyWorker ... Network connection lost`，客户端同时出现连接拒绝、HTTP 500 与超时。复测认证有 3167 个完整 HTTP 500 和 21 个 500 响应接收超时，没有 Server-Timing 的失败无法细分为 Worker 内部问题。
3. Worker 外等待包含 HTTP 连接池、连接建立、网络和本地代理；未做绕过代理的受控对照，不能仅凭此字段断言代理是唯一根因。
4. 上传有明确的 Worker 内部慢阶段：R2.put P95 为 13.06s / 16.59s。它包含流式接收请求内容与写存储的等待，不能进一步断言是磁盘本身慢。流式传输已经存在，改成流式并不能消除这项问题。
5. 大量超时发生在客户端门控队列中或剩余超时预算不足时。失败与成功延迟分开输出；收到 200/201 响应头但没有完整接收响应体仍算失败，不自动重试不确定的写入。
6. 压测脚本原先把指令刷新发往不存在的 `/veto/directives`，基线 506 个返回 404 的请求属于脚本问题（498 个完整响应、8 个接收超时），复测改用 `/veto/directives/mine`。

## 本轮 API 修改与证据

- 四个业务模块原先将通知中间件挂在 `*`，跨模块累积。用拥有多主题权限的真实 WS 回归测试确认：一次文件上传会收到 files、news、directives、situations 四种失效通知。现在每个模块只匹配自己的路径，同一测试只收到 files。
- 文件 `/broadcast` 原先按连接分别验证 token、每个连接重复扫描所有事件。现在按大会一次查询有效会话，事件先按席位分组。回归测试在旧实现记录三个接收连接对应三次查询，修复后一次；只向匹配席位发送，旧 token 关闭码仍为 1008。未增加跨请求权限缓存。
- 增加可选 `LOAD_DIAGNOSTICS` 计时，只在隔离本地环境启用。数据库/存储调用是 I/O wall time，不是 CPU profiler。

修改没有解决本地万人接入、R2 高尾延迟或整体超时。未开展第二轮优化。
