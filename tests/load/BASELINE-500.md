# 500 席本地测试基线（2026-11-11）

结论：**500 席本地短时在线验收未通过；尚无 Cloudflare 容量验收结论。**
不得据此承诺会议可以稳定承载 300 人或 500 人。

## 已实现的验收配置

- `conference-500`：同一大会至少 500 个独立席位，默认共同连续在线 1,800 秒，混合业务。
- `files-500`：500 个席位共同在线 600 秒，各交 4 个文件，共 2,000 个文件；每席最多并行上传 2 个文件并校验下载内容。
- `conference-1000`：同一大会至少 1,000 个独立席位，默认共同连续在线 1,800 秒，混合业务。
- `files-1000`：1,000 个席位共同在线 600 秒，各交 4 个文件，共 4,000 个文件；每席最多并行上传 2 个文件并校验下载内容。
- `conference-2000`：同一大会至少 2,000 个独立席位，默认共同连续在线 1,800 秒，混合业务。
- `files-2000`：2,000 个席位共同在线 600 秒，各交 2 个文件，共 4,000 个文件；每席最多并行上传 2 个文件并校验下载内容。
- 同一窗口逐席计分：全部 VU 必须在固定绝对时间窗持续 ready，迟到、掉线或提前结束均失败。
- 在线窗口需要不同 seatId、至少 500 个真实账号，且 credentials 中声明同一个 conferenceId；认证身份还会逐席对照。

## 本地试跑

运行于本地隔离 Wrangler Worker + D1/R2/DO，500 个测试席位通过真实邀请认领接口创建，完成代表性业务 smoke。主机为 Intel Core Ultra 9 275HX、24 逻辑核心、约 32GiB RAM。两次 VU=500 的 browse 短测使用共同 60 秒窗口；一个用 10 批爬坡，另一个用均匀爬坡。均未达到通过标准：

| 爬坡         |        认证成功 |        WS 就绪样本 | 完整在线窗口 | HTTP 失败率 | HTTP P95 | 结果   |
| ------------ | --------------: | -----------------: | -----------: | ----------: | -------: | ------ |
| 10 批 / 120s | 392/500 (78.4%) | 392 次中 392 ready |        2/500 |       36.9% |    19.9s | 未通过 |
| 均匀 / 120s  | 341/500 (68.2%) | 341 次中 333 ready |        5/500 |       31.8% |    22.8s | 未通过 |

机器实际运行了仓库提供的本地 Wrangler ProxyWorker；日志记录请求重试及 “Network connection lost”，所以这些数字是**本地开发拓扑的失败基线**，不能单独推断 Cloudflare 线上 Worker/D1/DO 的极限。第二轮均匀爬坡仍失败，说明仅靠放平登录洪峰不足以通过。两次均保留了真实独立会话以及完整共同窗口阈值，没有通过放宽门槛制造通过结果。

- `results/2026-11-11T05-43-38-168Z-0cc52b9f-2e7f-4f9e-8c73-cb8ad3f45323/report.md`

小规模 2 席真实在线窗口 smoke 通过，用来核实窗口计分和绝对起止时间写入正确，不表示容量通过。压测代码 TypeScript 检查通过，144 个 load 套件测试通过。

## 1000 席本地短测

在同一隔离本地 Wrangler Worker + D1/R2/DO 环境中，又创建了 1,000 个独立席位，并执行了经请求校准的 `browse` 测试：180 秒爬坡、60 秒准备、60 秒共同在线窗口、`--open-loop-seed 1776`。它不是纯只读负载：`conference-1000` 配置 `observerEvery: 5`，而当前 `main.ts` 对 observer 启动 reviewerLoop。结果仍未通过：

| 指标                   |             结果 |                        要求 |
| ---------------------- | ---------------: | --------------------------: |
| 认证成功               | 838/1000 (83.8%) | 1000/1000；过程目标至少 90% |
| WS ready               |          838/838 |        所有已认证席位 ready |
| 完整共同在线窗口       | 677/1000 (67.7%) |                   1000/1000 |
| HTTP 失败率            |           11.66% |          ≤1%；过程目标 ≤10% |
| HTTP P95               |           17.95s |                         <2s |
| ProxyWorker 最终错误   |         2,256 次 |                           0 |
| ProxyWorker 重试后恢复 |         8,674 次 |      仅作诊断，不算成功席位 |

1000 席的 Worker 列表请求曾达到约 15 秒；k6 发压进程内存约 893MiB，两个 workerd 进程约 630MiB 与 940MiB。Local Explorer 记录了顶层 GET `ok`、未完成 outcome 和 `responseStreamDisconnected`，与 500 席校准轮的本地 ProxyWorker 连接流断开模式一致。`files-1000` 的 4,000 文件提交本轮没有执行，因为在线与初始读取层已经未通过；不能把它写成文件业务测试通过或失败。

## 校准负载后的定位结果

随后对 `browse` 的请求量做了校准：每个席位在收到 WS `ready` 后只执行一次初始列表读取，不再重复执行启动刷新；没有 observer 的 browse 不会启动审核队列轮询或周期浏览刷新；另外支持 `--open-loop-seed` 对爬坡时刻增加可复现的 0–499ms 微分散。注意，500/1000 专用 profile 设置了 `observerEvery: 5`，当前 `main.ts` 仍会令每第 5 席启动 reviewerLoop，因此这两轮不能称为纯只读基线。压测输出 `samples.json`，按认证、初始加载、在线窗口和业务阶段保留请求操作、状态和耗时；本地启动也开启 Wrangler Local Explorer observability。

校准轮仍使用 500 席、120 秒爬坡、60 秒准备和 60 秒共同在线窗口。结果为：认证 `479/500 (95.8%)`，WS ready `479/479`，共同窗口完整覆盖 `373/500`，HTTP 失败率 `11.6%`，HTTP P95 `7.8s`。`samples.json` 进一步显示失败包括 700 个状态码 0 的初始加载传输失败、21 个认证 HTTP 500、12 个初始加载 HTTP 500，以及在线阶段 19 个状态码 0 的传输失败。相较两轮原始 browse 测试的 `68.2%–78.4%` 认证成功率和 `31.8%–36.9%` HTTP 失败率，请求校准显著降低失败，但测试仍不是纯浏览，并且并未达到 90% HTTP 成功率或上线门槛。

旧版 Local Explorer 汇总曾被解读为没有顶层 5xx、最有证据指向 ProxyWorker；这与本轮 k6 样本记录的 21 个认证 500 和 12 个初始读取 500 不一致。Wrangler 日志还记录 2,089 个 `Error inside ProxyWorker ... Network connection lost` 和 5,656 个重试后恢复事件，但目前没有足够的请求 ID 将每条客户端失败、Worker/DO/D1 子调用及代理错误一一关联。因而只能确认本地运行同时出现了大量响应流断开和客户端观察到的 HTTP 500；不能据此认定所有状态码 0 都由代理造成，也不能解释 500 的内部根因或响应所属层。D1/DO 汇总没有明确业务错误 outcome 也不能排除排队、延迟或未被当前观测捕获的问题。Cloudflare 线上是否存在同类行为仍未知。

请求阶段与失败类型已有 k6 样本，ready/close 也记录实际连接上下线和持续时长；但客户端样本目前没有保留响应体或服务端 request ID，不能将 500 归到具体异常或资源。下一步先补齐脱敏的服务端异常上下文和跨层 request ID，并纠正 observer 的场景口径，再用同一负载对比本地入口、单独工作流和 Cloudflare 测试部署；依据 Worker、D1、R2、DO 以及发压端的同窗指标确认瓶颈。不能先假定是 ProxyWorker 限制，再据此决定是否修改服务端。

## Cloudflare 验收前置

当前没有实际 Cloudflare 测试地址、部署版本或 500 个已认领的隔离测试席位，所以**尚未连接 Cloudflare、尚未发送任何云端压力流量**。部署验收须使用真实 HTTPS/WSS 测试入口，逐步跑 smoke、`conference-500`、`files-500`；并把报告时间窗与 Cloudflare Workers、D1、R2、Durable Objects 的 Metrics/Logs 对齐。任何 429、资源限制、失败状态、发压端上行瓶颈都要保留原始分类。

不需要 KV 配置；KV 不会让请求更快，也不会修复 Worker、D1、R2 或 Durable Object 的瓶颈。将来若把负载数据迁入 KV，需把它当作独立改动另行测读写、延迟、限额及一致性。
